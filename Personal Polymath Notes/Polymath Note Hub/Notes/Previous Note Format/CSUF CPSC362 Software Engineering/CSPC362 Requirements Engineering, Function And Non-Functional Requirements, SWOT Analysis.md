___
**Requirements Engineering**
* Collecting the requirements and drawing up prior documentation.
* The stakeholder's expectations in what the product should do or a goal it achieves.
* **User Requirements:** What does the user experience? What will the user do? What is required of the user?
* **System Requirements:** Microservices and operations. What should be implemented? 
* **Performance Requirements**
* **Security Requirements**
___
**Function Requirements, Non-Functional, Domain Requirements**
* **Functional:** What should it do? What is the output? What is expected?
* **Non-Functional:** Not necessary (but desirable), how well the system should perform. Hardware limitations & responsiveness, hard definitions.
* **Domain:** Set of guidelines that product should work withing (frameworks)
___
**Requirement Imprecision**
* Requirements need to be precise, they cannot be vague
___
**Requirement Completeness And Consistency**
* Requirement should be complete (detailed) and it should be consistent (non-conflicted with other requirements)
* **Functional And Non-Functional** are two sides of the same coin.
___
**Non-Functional Requirements (There Is Priority)**

**Requirement Specification**

___
**Requirements And Design**
* Should state the relationship between requirements and the design.
* There may be a level of exploration and adaptation of other systems and architecture to support your product.
	* Isolation of subsystems.
	* Monolithic subsystems
	* Maybe be legal based and government based
___
**Natural Language Specification**
* Requirements written in common natural language to understand the behavior of your product.
* Should be peer-reviewed for clarity
* Highlight systems that are important to connect each subsystem.
* Can lack clarity, requirements may be not well defined, requirements can be mixed up.
___
**Structured Specification**
* There is a formal approach that persists throughout the development cycle; follows the organization's specifications.
___
**Form-Based Specifications**
* Describes the input and output, enables actions and mathematical reasoning to formulate a cohesive input and output language; how its being transmitted or calculated.
___
**Tabular Specification**
* Often used with natural language and often describes range of ways certain data is calculated for a certain output.
	* Think game controller or game logic.
___
**Software Requirement Document**
* Documents what it should do, not how to do it.
___
**System Requirments**
* System Customers: give input on what is required of the system
* Managers: Utilize planning and legal methodologies
* System Engineers: Use the requirements to develop a system.
* System Test Engineers: Use the requirements to develop tests for the requirements.
* System Maintenance Engineer: Provides methods to maintain and keep accessibility of an application.
___
**Structure Of The Requirements Document**
* Preface: Defines the readership of the document, version of the document, past edits, revisions.
* Introduction: System functionality and sub-system functionality 
* Glossary: Define technical terms used in the document
* User Requirements Definition: Services provided to the user
* System Architecture: High-level overview of the anticipated system architecture.
* System Requirements Specifications: function and non-functional requirements.
* System Model: Graphical systems: UML and data flow
* System Evolution: Anticipating changes for a system, hardware, software, etc.
* Appendices: 
* Index: General tables and information
